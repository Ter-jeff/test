# Test Commands
- Always run unit tests using Release configuration: `dotnet test -c Release`
- Do not use default Debug mode compilation.

# Lint / Format Checking
- Jenkins' Lint stage runs: `dotnet format --verify-no-changes --exclude-diagnostics CA1502 CA1505 --exclude ./Cautogen/` from `01_Code/ProjectAutomation`. This exact command has repeatedly and non-deterministically returned a false "clean" result locally (instant 0-byte output, exit 0) even on confirmed-broken files — do not trust a clean run of this exact invocation as proof Jenkins will pass. Root cause was never confirmed; candidates include stale MSBuild node-reuse processes left running by Visual Studio, or general flakiness analyzing this ~28-project solution. Adding `--verbosity diagnostic` or dropping `--exclude-diagnostics` did NOT reliably fix it either — a later side-by-side test showed the exact original flag combo working fine unchanged, so treat any single "it worked that time" as inconclusive, not a fix.
- If a clean local run seems suspicious (e.g. near-instant with 0 bytes of output on a large solution, when a real run normally takes 30-80s and prints per-project analyzer progress), don't trust it — rerun once or twice, and cross-check against actual Jenkins output before believing local is clean.
- `Cautogen/` has many pre-existing WHITESPACE issues unrelated to any current branch work — always exclude it (`--exclude ./Cautogen/`) or filter it out of results before triaging.
- When programmatically splitting a long single-line object/array initializer into multi-line C# (e.g. via a Python script), always join lines with `\r\n`, never `\n` — this repo's `.cs` files are CRLF throughout, and a stray `\n` join produces an `ENDOFLINE` lint error on every line it touches.
- This repo's `.editorconfig` requires, for every `.cs` file: `charset = utf-8-bom`, `end_of_line = crlf`, AND `insert_final_newline = true`. Any NEW `.cs` file must have a UTF-8 BOM (`EF BB BF`), CRLF line endings throughout, AND end with a trailing `\r\n` after the final `}` — or Jenkins' Lint stage fails with `error CHARSET: Fix file encoding.`, a separate `ENDOFLINE` error, or `error FINALNEWLINE: Fix final newline. Insert '\r\n'.` respectively. The Write tool creates brand-new files with NO BOM, LF-only endings, and NO trailing newline by default — this is not limited to the script-splitting case in the line above, it happens for every new `.cs` file written this way, and these 3 issues surface across *separate* Jenkins runs (fixing BOM doesn't reveal the ENDOFLINE problem until the next run, and fixing that doesn't reveal FINALNEWLINE until the run after — check all three the first time instead of waiting for each error to appear one by one). After creating or bulk-rewriting `.cs` files, verify with `file <file>` (expect "UTF-8 (with BOM) text, with CRLF line terminators") AND check the last 2 bytes are `0d 0a` (`tail -c 2 <file> | xxd`) — a file can report correct BOM+CRLF via `file` and still be missing the final newline. Fix with a small Python snippet that reads the raw bytes, strips any existing BOM, normalizes `\r\n`→`\n`→`\r\n`, ensures the result ends with `\r\n`, and re-prepends the BOM (`b'\xef\xbb\xbf'`) before writing back; don't use PowerShell `Set-Content` for this (see the file-truncation risk noted separately).
